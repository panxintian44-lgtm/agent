# 联合验收与网页接线 v1.0

- 日期：2026-10-22。
- 状态：**本地组件联调 12/12 通过；候选修复待团队评审，原网页及真实模型全链路尚未联合验收。**
- 负责板块：第四板块，Safety / Risk / Eval（Vesper）。
- 目标：将已有日常资金规则、Core 风险交接、审批和模拟状态按同一任务验证清楚，并给原产品页面提供准确的接线依据。
- 本轮范围：本地回环 HTTP 联合验收与交接说明。只使用虚构用户、虚构资金和显式测试替身，不操作生产配置，不执行真实资金动作。

## 1. 用户要验收的三组行为

| 组别 | 用户场景 | 必须看到的证据 | 不通过的情况 |
| --- | --- | --- | --- |
| 正常路径 | 已确认现金与房租或学费预留后，安排仍有足够资金 | 模型提议、Risk ALLOW、签名回调、等待审批、签名审批、同任务模拟回执与审计关联 | Risk 通过就自动执行；等待审批显示为已完成；任务或方案串单 |
| 保护用途冲突 | 想继续投入，但会挤占已确认房租或学费 | 可复算资金缺口、Risk BLOCK 的具体原因、Core 拒绝状态、后续审批与模拟被阻止、无新占用或成功回执 | 模型一句话解除预留；用户勾选覆盖硬阻止；错误路径生成成功回执 |
| 审批后变更 | 用户已批准原计划，随后修改资金用途或相关参数 | 真实资金计划 revision 变化、原任务原方案摘要执行被拒、新任务按新版本重检并重新审批 | 只检查一个假摘要就宣称旧授权失效；修改后继续沿用原授权 |

三组共同要求：风险判定、审批与模拟结果关联同一任务。拒绝、异常、等待审批、回执未知期间，执行入口保持关闭。现有未接网关的阻断必须保留。

### 2.1 固定源码来源

- 本轮复用的 Risk 对话与回调能力来自 Vesper PR #27；实际使用的本地 Risk 提交由运行证据记录。
- Core 来源固定为同一团队仓库中的 PR #28 提交 `9e6bed133c36f7fa42fc15f4dc7a8791049b0841`。
- `joint-acceptance/run.cjs` 将该 Core 快照导出到临时目录，再仅覆盖经本轮评审的候选 `review-workflow.js`，不合并其他 Owner 分支，不操作生产。
- 证据必须分别记录固定 Core 基线 SHA、原始文件哈希与候选覆盖文件哈希。不能把带候选补丁的结果描述成“未修改的 PR #28 原版已通过”。
- Core 快照缺失、导出失败或校验失败时应明确中止；不能静默换用另一个分支。

### 2.2 本轮发现的能力边界问题与候选修复

兼容审计发现：固定 PR #28 原版的 `/api/review/simulate` 检查 Risk、审批、方案摘要和资金，但没有强制校验任务 `capability`。因此，`REVIEW_ONLY` 任务在满足后续 Risk 与审批后也可能生成内部模拟回执。这与原对话“只读分析”的能力声明不一致。

本轮追加最小候选修复：Core 模拟入口仅允许显式 `SIMULATION_ONLY`，`REVIEW_ONLY` 保持阻断；正向模拟测试也必须明确请求 `SIMULATION_ONLY`。本地联合脚本使用导出的固定基线与这一候选覆盖文件，并在报告中展示两者来源。

候选修复同时阻止只读任务经人工批准进入 `READY_FOR_SIMULATION`；顶层能力与原始已审查输入必须一致。缺失、未知或单字段改写都不会增加权限。已完成的历史回执允许重放，不新增占用。`NO_ACTION` 的只读任务沿用既有状态枚举保守停留在 `PENDING_APPROVAL`，执行能力关闭并记录能力不足原因；只读完成态如何展示由 Core／UI Owner 后续统一。

**这是待团队评审的源码候选修复，不是线上已修复的声明。** PR #28 既有公网服务、原产品页面和配置不会因本地验证自动更新。原 PR #27 对话仍保持 `REVIEW_ONLY`，不能为了跑通验收将其能力升为模拟。

## 3. 本地验收链路与证据标识

```text
虚构问题、资金事实及保护用途
  → 现有 Risk 资料归一化与程序评估
  → 固定 Core Worker Handler 创建模型提议与风险交接
  → Risk 校验同任务、原方案与程序结论
  → HMAC 签名回调
  → Core 等待用户审批
  → 已签名的审批服务测试请求
  → Core 内置 simulate 复查资金版本与授权
  → 内部模拟回执及可关联审计
```

以上链路通过实际本机回环 HTTP 传输请求，执行的服务逻辑是固定版本 Core Worker Handler、明确记录的能力校验候选覆盖，以及现有 Risk `normalize`、`assess`、回调草稿和 HMAC 代码。HTTP 成功只证明该次本地请求成功，不代表公网服务、真实模型或真实账户已接通。

正向模拟案例使用既有官方回调草稿和 HMAC 方法，直接向真实 Core Handler 发送签名 HTTP；它们不经过只接受 `REVIEW_ONLY` 的原回调发送器。`readonly_capability` 与 `unknown_callback_response` 两例才走完整的原 `createConversationReviewer → sendRiskCallback`。这些不同范围在报告中分别记录，不能统称为“原问答已接通审批执行”。

| 内容 | 必须使用的标识 | 能证明什么 |
| --- | --- | --- |
| 模型 | `TEST_DOUBLE` | 真实模型契约与后续模块可在固定输入下串接；不是供应商推理成功 |
| 审批 | `SIGNED_SERVICE_TEST_DOUBLE` | 受签名保护的审批 Handler、任务绑定和拒绝规则；不是已上线的终端用户身份体系 |
| 存储 | `TEST_STORAGE` | 本轮测试中的状态、记录和副作用计数；不是已验收的生产账本 |
| 模拟能力 | `SIMULATION_ONLY` | 本轮专用测试明确请求内部模拟；没有扩大原对话的 `REVIEW_ONLY` 能力 |
| 模拟回执 | `mode: SIMULATED`、`side_effects: false` | Core 内部模拟完成；真实资金操作未发生 |

真实模型调用数、真实资金动作数均应单独记录为 `0`。不能把测试替身计为真实模型调用或业务成交。

## 4. 同一任务的六项绑定

Risk 回调必须从 Core 返回的 Handoff 原样提取以下六项，不能以本地任务编号、用户输入编号或重新计算的猜测值替换：

| 字段 | 绑定内容 |
| --- | --- |
| `handoff_id` | 本次 Core 风险交接 |
| `task_id` | 本次 Core 任务 |
| `request_id` | Core 创建该任务时的请求 |
| `run_id` | 模型与工作流运行 |
| `audit_id` | Core 审计链 |
| `proposal_sha256` | Core 的完整拟议方案摘要 |

固定回调仍使用 `risk-callback.v1` 的十字段：上述六项，加 `callback_version`、`decision`、`reviewer`、`reason`。不加入金额、审批、资金版本等额外字段来修改动作。

- Risk 输出 `ALLOW / REVIEW / BLOCK / ERROR`。
- Core 回调为 `APPROVE / REQUEST_MORE_INFO / REJECT`，分别对应前三种有效业务结论。
- `ERROR` 暂停处理，不能映射为 `APPROVE`，也不能伪装成普通资料补充成功。
- Risk 结果与审批结果各自记录，Risk `APPROVE` 不等于用户已批准。
- 方案摘要使用 Core 原始方案规则；不能把请求指纹或排序后的另一份 JSON 摘要当成方案摘要。
- 同一回调重试必须完全复用已有内容。补资料或修改方案后使用新任务重新评估，不能覆盖已冻结的旧回调。

审批与模拟继续绑定原 `task_id` 与 `proposal_sha256`；六绑定中的其他编号应通过同一任务记录关联保留。

## 5. 权限、签名与用户审批的区别

| 机制 | 证明或限制的对象 | 不能替代什么 |
| --- | --- | --- |
| 服务机器凭据 | 请求来自持有服务端凭据的调用方 | 用户本人确认、完整业务权限 |
| `X-Risk-Signature` 与固定 Risk 审核身份 | Risk 回调由配置的服务签名，且审核身份与 Core 配置一致 | 终端用户审批、真实资金执行许可 |
| `X-Approval-Signature` | 审批请求来自受信任审批服务且正文未被修改 | 用户登录身份的取得、原页面的本人确认交互 |
| 明确的用户完整计划确认 | 用户同意某任务、方案与资金用途版本下的动作 | 硬性风险阻止、过期授权、变更后的新计划 |
| 执行前复查 | 当前版本、资金、Risk、审批与幂等条件仍满足 | 外部执行网关的可信回执 |
| PAPER 回执 | 指定模拟层的执行结果 | 真实买卖成交或实际银行付款 |

所有机器凭据与签名密钥只在服务端配置。浏览器不提交 Risk 决定、审核人、审批签名或可信用户身份。CORS、分享链接、账号 Invite 和一段“用户已批准”的备注都不能代替这些机制。

原页面收集“事实确认”和“保护用途确认”是建立资金约束，不是对投资或付款的执行授权。本轮审批测试替身也不能被包装成已完成真实用户身份验证。

## 6. 三组案例的最小检查点

所有金额均为虚构示例，不构成行业统一阈值。Core 资金计划金额用整数分，Core 动作的 `amount` 用元数值；对话输入的 `_yuan` 字段仍使用十进制原文字符串，避免浮点数静默舍入。

### 6.1 正常路径

建议例子：现金 10000 元，房租保护 4000 元，本次拟投入 2000 元，费用与其他占用已明确确认为 0。

1. 建立已确认虚构资金计划，绑定返回的 `funding_plan_id` 与 `funding_plan_revision`。
2. 创建显式 `SIMULATION_ONLY` 的测试任务，取得提议原文、运行编号、Handoff 与方案摘要。
3. 现有 Risk 规则返回 ALLOW，签名回调记录为 Core `APPROVE`。
4. 在审批前尝试模拟，必须阻止，回执仍为空。
5. 测试审批服务提交针对同一任务和同一摘要的已签名 APPROVE。
6. Core 内置模拟完成，回执关联原任务，仍为 `execution_allowed:false`、`side_effects:false`。
7. 重复同一请求或模拟动作，复用原记录和回执，不新增资金占用。

### 6.2 房租与学费冲突

房租、学费分别建立案例：现金 10000 元，保护用途 4000 元，拟投入 8000 元，费用与其他占用为已确认 0，程序缺口为 2000 元。

1. 允许展示诊断与模型解释，但程序判定 BLOCK。
2. Risk 回写 Core REJECT，保留原风险原因、资金缺口及证据引用。
3. 即使继续尝试审批或模拟，也必须拒绝。
4. 无成功模拟回执、无新增资金占用；审计保留拒绝与执行阻断事件。
5. 用户或模型不能通过改变备注、同意警告或声称已批准来放行。

### 6.3 审批后资金版本变化

从正常案例开始，在已完成 Risk 与审批、尚未模拟时，将服务端资金计划中的房租预留由 4000 元修订为 5000 元。

1. 通过真实 `/api/funding-demo/plan/revise` 路径修改计划，携带原 `plan_id` 与 `expected_revision`，使 revision 实际变化。
2. 再使用原 `task_id` 与原 `proposal_sha256` 请求模拟。
3. 必须因 `FUNDING_PLAN_CHANGED` 拒绝；没有回执与新增占用。不得只提交一个编造的摘要来代替此检查。
4. 历史审批可以保留当时 APPROVED 记录，当前执行资格必须失效；不要求把历史审批改写成另一段事实。
5. 使用新任务、新幂等编号与新资金 revision 重检。旧审批不能复制到新任务；新任务在未重新审批前同样不得模拟。

补充的参数变更保护：审批或模拟接口只接受固定白名单。额外金额字段、摘要不匹配或其他任务编号必须拒绝。该检查与“资金 revision 变化使旧授权无法执行”分别记录。

## 7. 接入原网页时的约定

本轮不新增展示站点。小果负责的原页面、原问答入口继续作为用户入口，林粹与 Vesper 对齐同一个后端任务链。

1. 用户问题、独立确认的金额事实与保护用途，经现有服务端代理提交。未知金额保留未知，未确认用途不标为已确认。
2. 现有对话路径保持 `REVIEW_ONLY`。验收脚本的 `SIMULATION_ONLY` 不得由普通浏览器字段悄悄注入，不放宽 PR #27 回调发送器的限制。
3. 页面分别显示：输入样例、模型实际原文、拟议动作、程序指标、Risk 决定及原因、审批状态、模拟状态、运行与审计编号。
4. `TEST_DOUBLE`、离线演示、真实模型调用明确区分。后端失败显示失败；已经算出的程序结果可以保留，但不能遮住模型或回调失败原因。
5. “等待审批”“审批已通过但未执行”“内部模拟已完成”“真实 PAPER 网关未连接”使用不同文案。
6. 修改金额、费用、用途、确认或问题后，旧结果标为失效；相同输入重试复用请求编号。UNKNOWN 先核查原任务，不自动生成新编号盲重试。
7. 若后续引入正式用户审批，服务端须先取得可信用户身份及当前计划确认，再签署请求。客户端传来的 `approver` 或 `approval:true` 不能直接取得权限。
8. 即使本地三组通过，仍不切换生产地址或开放真实执行；相关 Owner 审核部署与线上验收后另行记录。

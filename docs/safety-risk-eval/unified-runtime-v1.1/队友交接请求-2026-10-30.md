## 4. 字段与接口边界

以下是所需信息及对应语义，不是擅自发布的新公共接口。最终共享字段名和路由由架构／Core Owner统一。

| 信息 | 必须明确的语义 |
| --- | --- |
| 主体与任务 | 访客会话或可信本人身份的来源；主体/账户归属；任务、请求、运行、审计及方案摘要的对应关系。访客Cookie或HMAC服务认证不能代替本人批准 |
| 资金 | `CNY`及“元/整数分”；账面现金是否包含冻结；可用余额与占用如何核对；重复义务如何识别；关联占用覆盖金额和证据 |
| 用途与日期 | 用户明确确认的预留、尚待支付额、付款时间；收入已到账/预计、是否包含在余额中；不能为了通过而自动取消保护用途 |
| 完整度与版本 | 未知项、来源/日期/版本、画像/约束/方案与账本版本；必需与可选依赖的适用性由可信服务端提供 |
| Risk输出 | `ALLOW/REVIEW/BLOCK/ERROR`、原因/规则/证据/恢复动作；旁路`unified_assessment`的五档、覆盖、`validation_status/errors`及历史检查引用；工作台另有`current_validation` |
| 失败 | 超时、结果矛盾、不支持版本、审计或存储失败要返回明确错误和允许的恢复动作，不用离线答案伪装模型成功 |

冻结的`risk-callback.v1`仍是十字段：`callback_version, handoff_id, task_id, request_id, run_id, audit_id, proposal_sha256, decision, reviewer, reason`。本次只读评级扩展放旁路对象或审计；不能把评级、用户批准或账户字段直接塞进冻结回调。

`ALLOW→APPROVE`、`REVIEW→REQUEST_MORE_INFO`、`BLOCK→REJECT`是既有Core回调映射。**APPROVE表示Risk审核结果，不等于用户本人批准。**`ERROR`不发送伪成功回调。

不要把Sites工作台的整份独立Worker复制成团队第二套审批或扣款服务。优先提取纯规则/评级/权限函数及其所需配置，复用现有主服务的可信上下文、存储与统一入口。

## 1. 用户会看到什么

原 `/risk` 页面增加“连接与服务状态”，分别展示工作台、数据存储、远程 Core 与模型配置状态。

- 浏览器报告离线时立即提示并暂停新提交，不等待下一轮探测。
- 普通服务故障在下一次健康检查或当前请求报错时提示，并非保证故障发生瞬间发现；没有关闭页面后的全天候监测。
- 页面可见且在线时，按约 30 秒间隔进行只读健康检查；隐藏到后台暂停轮询，返回前台重新检查。
- 恢复网络只触发健康检查，**不自动重发任何业务操作**。
- 存储或服务状态无法核实时，相关提交暂停；远程 Core 不可达时，模型调用暂停，不切换成离线成功。
- 页面提供“重新检查连接”；有原任务编号时可只读查询原任务，查询不等于重新执行。

浏览器的在线／离线事件只是本地连接信号。是否能访问工作台和远程 Core，仍以服务探测为准。

## 2. 请求时限

| 请求类型 | 时限 | 超时后的处理 |
| --- | --- | --- |
| 普通读取 | 10 秒 | 显示读取失败，可由用户重新查询 |
| 普通提交 | 20 秒 | 停止等待；若无法确认服务端结果，保留标识并暂停后续提交 |
| 模型请求（`model-demo`／`model-review` 等模型入口） | 65 秒 | 明确显示超时或结果待核查，不生成成功结果，不自动再次调用模型 |
| 前端健康检查 | 7 秒 | 无法核实状态时暂停提交 |
| 服务端存储与 Core 探测 | 每项最多 4 秒，并行执行 | 各自报告不可用，不用一个组件的成功覆盖另一个组件失败 |

服务端健康结果使用 **20 秒内存缓存**，并合并同一运行时内的并发探测。没有后台定时任务，不写健康检查日志到用户业务审计。

客户端停止等待或取消网络请求，不代表服务端已经取消操作，因此不能据此自动重试。

## 3. 提交前先保存待查标记

每个提交请求必须先把 `IN_FLIGHT` 标记写入当前标签页的 `sessionStorage`，并读回确认保存成功；**会话存储不可用时不发送请求**。

标记只保留接口路径、原任务编号、幂等编号、状态与时间，不保存资金金额、账单备注、Cookie、CSRF 或服务凭据。

```text
保存 IN_FLIGHT 标记成功
  → 发送一次请求
  → 已取得可核实结果：清除对应标记
  → 结果无法确定：保留原标识，标为 UNKNOWN，暂停新提交
```

等待结果期间即暂停其他提交。超时、断网或响应无法验证时，不通过生成新编号来绕过待查保护，也不把未知结果显示成“未执行”或“已完成”。

### 如何恢复

1. 有任务编号：用户主动查询原任务与回执。
2. 只有匹配原执行幂等编号的终态回执，才可解除对应执行请求的待查保护。
3. 读到了旧任务，不代表本次修改或提交已经完成；其他变更仍需对应 Owner 核查关联记录与审计。
4. 尚无任务编号、查询失败或回执不匹配：继续暂停，交团队核查服务端记录，不重新创建请求。

### 同标签页限制

`sessionStorage` 只用于当前标签页会话内的保护。同一标签页刷新或恢复时，可以读取尚未清除的待查标记；**不保证跨标签页、跨设备、关闭标签页后或清理浏览器数据后的恢复**。

因此，这不是共享资金账本、持久任务恢复系统或服务端幂等机制的替代品。不能以“新开页面没有标记”为理由认定原操作失败并重新执行。

## 4. 健康接口的含义与边界

新增同源只读 `GET /api/safety/health`，在原会话初始化前处理：

- 工作台：该健康 Handler 已响应。
- 存储：只执行 `SELECT 1 AS ok`，不读取用户业务资料，不创建会话、不写数据库。
- Core：固定读取原远程 Core `/health`；拒绝跳转、限制响应大小，并校验服务和契约标识。
- 模型：只显示 Core 声明的配置状态，未知时保留未知。

正常探测返回 `risk-service-health.v1`，组件失败使用 `DEGRADED` 分项说明；健康 Handler 本身异常才返回明确失败。

应用健康 Handler 不创建业务会话。线上边缘平台可设置自己的 `__cf_bm` Cookie，不能据此声称整个 HTTP 响应绝对没有 Cookie。

以下字段固定保持：

```json
{
  "inference_probe": "NOT_RUN",
  "business_acceptance": "NOT_VERIFIED",
  "execution_allowed": false
}
```

其中 `inference_probe` 位于 `services.core`。健康检查已响应或模型“已配置”，均不证明模型推理成功、风险回调成功、用户已批准或整个业务链路已验收；不因此开放执行权限。

## 7. 前端可见错误提示补充（2026-10-23）

在页面当前视口增加固定错误通知，滚动到下方仍可见；原操作区继续显示简短提示。

- 显示操作名称、中文原因、处理状态、下一步与原因代码；有可信原任务编号时可查询原任务。
- 区分“尚未发送”“服务已拒绝”“读取失败”和“原结果待核查／仍在处理”，不把未知结果写成成功或确定失败。
- 提示不自动消失，健康检查成功不会覆盖用户操作错误。用户可关闭通知；关闭不解锁、不取消、不重发。
- “检查连接”和“核查原任务”只触发只读查询，没有自动再次提交按钮。
- 提示使用固定原因代码与中文文案；不直接展示原始服务错误、响应正文、堆栈或凭据。
- 本地异常通过现有 action/run 的 catch 接入。业务 BLOCK 的风险结论仍由原风险区域解释，不混为网络错误。
